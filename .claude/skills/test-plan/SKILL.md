# Тест-план за документацією SkyPermit

Мета — дати QA-інженеру документ на одну сторінку, з яким можна піти на
планування: що тестуємо, чого не тестуємо, де найбільші ризики, що робимо
руками, а що варто автоматизувати, і коли вважаємо роботу завершеною.
Читатимуть його люди, які знають продукт, тож план має бути щільним, без
переказу документації: деталі — посиланням на розділ docs.

## Вхід

Користувач передає файл (`../skypermit/docs/02-state-machine.md`) або
директорію (`../skypermit/docs/`). Шлях може бути відносним, коротким
(«02», «state machine», «API») — зіставляй з файлами в `../skypermit/docs/`.
Якщо незрозуміло, про який документ ідеться, перепитай одним реченням.

## Порядок роботи

### 1. Прочитай джерела

- Переданий файл / усі файли директорії — повністю.
- Завжди додатково: `05-open-questions.md` (статус відкритих питань) і
  `07-clarifications.md` (виправлення, що мають пріоритет над `06`). Навіть
  якщо план про API, відкрите питання може блокувати частину скоупу.
- Інші docs — лише ті розділи, на які посилається скоуп (наприклад, план за
  `02` майже напевно потребує правил скасування з `06 §5`).

Ієрархія при суперечностях: `07` > `06`; статус «відкрито/вирішено» береться
тільки з `05`; `08` — похідний від `01`/`02` і поступається їм. Суперечність
між документами — це не те, що треба тихо розв'язати, а ризик, який треба
назвати (див. крок 3).

### 2. Точкова звірка з кодом (лише для ризиків)

Стратегія і скоуп будуються **тільки з docs** — план описує очікувану
поведінку, а не поточну реалізацію. Код потрібен лише для одного: знайти
місця, де реалізація вже розходиться з docs, бо це найконкретніші ризики.

Звір 2–5 ключових тверджень зі скоупу з відповідними файлами, не більше —
це не код-рев'ю:

| Скоуп | Де дивитись |
|---|---|
| Модель даних | `../skypermit/supabase/migrations/*.sql` |
| Стейт-машина | `../skypermit/lib/state-machine.ts` |
| Гейти | `../skypermit/lib/gates/*.ts`, `lib/curfew.ts` |
| API | `../skypermit/app/api/v1/**/route.ts`, `lib/http.ts`, `lib/auth.ts` |
| Фронтенд | `../skypermit/app/**` (пошук `data-testid`) |

`../skypermit` — **лише для читання**: жодних змін файлів, git-операцій,
що змінюють стан, `npm`-команд, міграцій; не відкривай `.env*`. Якщо
розбіжність знайдена — це «потенційний дефект» із посиланням
`файл:рядок`, не виправлення.

### 3. Сформуй ризики

Збери з чотирьох джерел і пріоритезуй (Високий / Середній / Низький) за
ціною помилки в продакшені:

1. **Відкриті питання з `05`**, що зачіпають скоуп — з номером питання.
   Поведінку за ними не вигадуй; відповідні перевірки — «заблоковано до
   рішення по #N».
2. **Суперечності між docs** — `06` vs `07`, docs vs міграції, застарілі
   формулювання (напр. «no login» у `04`, яке вже неправда для операторів).
3. **Критичні бізнес-правила** — чотири гейти (`PILOT`, `AIRCRAFT`, `ZONE`,
   `TIME_WINDOW`) і порядок їх оцінки, недозволені переходи (`409`),
   авторизація оператора vs ідентичність рецензента (`X-Reviewer-Id`),
   дедлайн скасування.
4. **Розбіжності docs і коду** з кроку 2.

Кожен ризик — один рядок: що може піти не так, наслідок, джерело.

### 4. Розподіли стратегію «вручну / автоматизовано»

Рішення приймай за природою вимоги, як вона описана в docs:

**Кандидати на автоматизацію** — детерміновані правила з чітким
очікуваним результатом, що повторюватимуться в регресії:
- пороги й межі гейтів (вагові категорії, currency пілота, часові вікна) —
  ідеальні для параметризованих тестів на граничних значеннях;
- матриця переходів стейт-машини, включно з усіма недозволеними (`409`);
- API-контракт: коди відповідей, формат помилок, `rule_reference`;
- UI-сценарії, для яких `04` фіксує `data-testid` — придатні для e2e.

**Вручну** — те, де потрібне людське судження або вимога ще рухається:
- дослідницьке тестування потоків і ролей (перемикач ролей, оператор vs
  рецензент);
- місця, зачеплені відкритими питаннями або суперечностями — автоматизувати
  поведінку, яку ще не визначено, означає закріпити здогадку;
- UX/читабельність повідомлень, яких docs не формалізують.

Для кожного пункту стратегії коротко вкажи «чому» — це те, що читач
захоче оскаржити або підтвердити.

### 5. Напиши план

Обсяг — **до ~600 слів** (одна сторінка A4). Якщо не вміщується, скорочуй
переказ, а не ризики: посилання на розділ docs замість пояснення правила.
Таблиці й списки, без вступних абзаців.

Збережи в `test-cases/plan-<скоуп>.md`, де `<скоуп>` — коротка назва
латиницею в kebab-case (`plan-state-machine.md`, `plan-api-contract.md`,
`plan-full-docs.md`). Якщо файл уже існує — спитай, перезаписати чи
створити нову версію. Директорію `test-cases/` створи, якщо її немає.

Шаблон:

```markdown
# Тест-план: <скоуп>

**Джерела:** <файли docs із розділами> · **Дата:** <РРРР-ММ-ДД>

## Скоуп
- <функціональна область> — <docs-розділ>

## Поза скоупом
- <що не тестуємо> — <чому: інший план / заблоковано #N / не наша відповідальність>

## Ризики
| # | Ризик | Пріоритет | Джерело |
|---|---|---|---|

## Стратегія
| Область | Підхід | Чому |
|---|---|---|
| <область> | Автоматизовано / Вручну | <коротко> |

## Критерії входу
- <середовище піднято, міграції застосовано, відкриті блокери з'ясовано…>

## Середовище й дані
- **Ролі:** <оператор (Supabase Auth) / рецензент (X-Reviewer-Id)>
- **Дані:** <оператори, пілоти, ПС у різних вагових категоріях, зони…>

## Критерії готовності
- <вимірювані умови: усі переходи з 02 покриті, 0 відкритих High-дефектів…>
```

Критерії готовності мають бути перевірюваними (кількість, покриття
конкретного розділу, статус дефектів), а не «тестування завершено якісно».

### 6. Відповідь користувачу

Після збереження — шлях до файлу і 2–3 речення: найважливіший ризик і що
заблоковано відкритими питаннями. Сам план у чат не дублюй.
