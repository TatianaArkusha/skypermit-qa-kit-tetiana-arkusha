# CLAUDE.md

Інструкції для Claude Code у цьому репозиторії.

## Мета

Це QA-кит для проєкту **SkyPermit** — системи реєстрації операторів дронів,
пілотів і повітряних суден та подання/розгляду заявок на польоти в зонах
повітряного простору. Сам продукт лежить у сусідній директорії
`../skypermit` (Next.js + Supabase).

Основна робота тут — **генерація тест-кейсів і тест-планів** на основі
документації з `../skypermit/docs/`. Це ручна/аналітична QA-документація,
**не автоматизовані тести**: не пиши код тестів (Vitest, Playwright тощо),
якщо я прямо про це не попрошу.

## Джерела вимог

Читай `../skypermit/docs/` перед генерацією будь-яких кейсів:

| Файл | Що там |
|---|---|
| `01-data-model.md` | 7 сутностей, поля, обмеження |
| `02-state-machine.md` | 7 станів `FlightRequest`; будь-який перехід поза схемою → `409` |
| `03-api-contract.md` | ендпоінти `/api/v1`, автентифікація (оператори — Supabase Auth, рецензенти — заголовок `X-Reviewer-Id`) |
| `04-frontend-spec.md` | дві ролі, UI, контракт `data-testid` |
| `05-open-questions.md` | **канонічний** статус відкритих питань |
| `06-business-rules.md` | правила гейтів із цитатами на першоджерела (`OH-1`, `ZC-2026.1`, `A-7`…) |
| `07-clarifications.md` | відповіді власника бізнес-правил — мають пріоритет над `06` |
| `08-uml-diagrams.md` | похідні діаграми; не є джерелом істини |

Пріоритет при суперечностях: `07` > `06`; статус «вирішено/відкрито» — лише
з `05`; `08` поступається `01`/`02`.

Також можна читати код і тести в `../skypermit` (`app/`, `lib/`, `supabase/`,
`tests/`), щоб уточнити поведінку, але **документація — це очікувана
поведінка**. Якщо код розходиться з docs — це потенційний дефект, познач
його, а не підганяй кейс під код.

## Обмеження щодо `../skypermit` — лише читання

Заборонено:

- створювати, редагувати, перейменовувати чи видаляти будь-які файли в
  `../skypermit`;
- виконувати там git-операції, що змінюють стан (`commit`, `checkout`,
  `reset`, `stash`, `pull`, `push`, створення гілок тощо);
- запускати команди, що змінюють середовище або дані: `npm install`,
  `npm run build`, міграції Supabase, скрипти, що пишуть у БД;
- читати чи виводити вміст `.env*` та будь-які секрети.

Дозволено: читати файли, шукати по них, `git log`/`git diff`/`git show`
лише для перегляду. Якщо для задачі потрібна зміна в `../skypermit` —
опиши її тут текстом і зупинись.

## Правила для тест-кейсів

- Кожен кейс має посилатися на джерело вимоги: файл і розділ
  (напр. `02-state-machine.md`, `06-business-rules.md §1.2`).
- Покривай позитивні, негативні та граничні сценарії; для стейт-машини —
  і недозволені переходи (очікуваний `409`).
- Для UI-кроків використовуй селектори з контракту `data-testid` у
  `04-frontend-spec.md`.
- Не вигадуй поведінку, якої немає в docs. Якщо питання відкрите в
  `05-open-questions.md` — познач кейс як заблокований і дай посилання на
  номер питання.
- Формат і шаблон кейсів зафіксуємо окремо (ймовірно, як скіл у
  `.claude/skills/`); до того — Markdown з полями ID, назва, джерело,
  передумови, кроки, очікуваний результат, пріоритет.
